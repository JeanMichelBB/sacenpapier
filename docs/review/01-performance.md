# Phase 1 — Frontend Performance Review

Reviewer role: frontend performance engineer. Evidence drawn from `docs/review/00-baseline.md` (§2 Lighthouse, §4 network) and direct inspection of the files cited.

| ID | Severity | Area | Problem | Evidence | Fix | Effort |
|---|---|---|---|---|---|---|
| P-1 | P1 | Client/server split | `Hub.tsx` is a single 634-line `"use client"` component rendering the entire homepage (header, nav, project preview, pod badge, latency ping, footer). Nothing on `/` is a server component except the thin `page.tsx` wrapper. | `src/components/Hub.tsx:1` (`"use client"`), `src/app/page.tsx:5-8` (passes all data straight into it) | Split into server components for static chrome (header text, nav, tag lists) and keep only interactive bits (`ThemeToggle`, `LanguageToggle`, ping/pod widgets, crush button) as client leaves. | L |
| P-2 | P1 | Data over-fetch | `getAllPosts()` returns every post's full `sections` body (not an excerpt), and `page.tsx` passes **all** 17 postmortems + 49 updates with full bodies into the client component `Hub`. `PostCard.tsx` only ever reads `title`/`duration`/`summary`/`tags`/`date` — `sections` is never used on the homepage. | `src/lib/posts.ts:5-13` (`sections: {label,body}[]` on `Post`), `src/app/page.tsx:5-8`, `src/components/PostCard.tsx:9-29` (no `post.sections` read) | Strip `sections` before passing postmortems/updates to `Hub`, or add a `getAllPostsSummary()` that omits body text; full body stays in `getPost()` for detail pages only. Baseline content inventory: 7,301 + 12,481 words currently round-tripped unused. | S |
| P-3 | P1 | Homepage LCP | Homepage mobile LCP is 6.7s vs 2.1–2.7s on every other page (Perf score 66 vs 97-100). Baseline attributes this to the embedded iframe + polling captured in page-load cost. | `docs/review/00-baseline.md` §2 table, §2 note under table | See P-4/P-5/P-6 below — the iframe eager-loads and cache-busts, and polling starts on mount; both compete for mobile network/main-thread during the LCP window. | — (tracking row) |
| P-4 | P1 | Iframe cost | `ScaledFrame`'s `<iframe>` has no `loading="lazy"`, loads immediately on mount, and its `src` is cache-busted with `_t=Date.now()` on every page view — defeating HTTP caching of the embedded app's own assets on every single visit. | `src/components/ProjectPreview.tsx:101-104` (`setBustedSrc` with `Date.now()`), `:118-133` (`<iframe src={bustedSrc}>`, no `loading` attr) | Add `loading="lazy"` (iframe is below the fold on mobile per the 9:16 aspect box) and drop the cache-bust, or move it behind a user-triggered "refresh preview" action instead of running on every load. | S |
| P-5 | P2 | Polling behavior | Backend-latency polling (`/api/backend-latency`) fires immediately on mount (`poll()` called synchronously inside the `useEffect`) and then every 10s indefinitely while the homepage tab is open, each call fanning out to 4 cross-origin health checks server-side with no timeout. Baseline confirmed 5 calls in the first 15s. | `src/components/Hub.tsx:144-170`, `src/app/api/backend-latency/route.ts:9-20` (`fetch(url,{cache:"no-store"})`, no `AbortController`/timeout), `docs/review/00-baseline.md` §4 | Defer first poll until after LCP (e.g. `requestIdleCallback` or a short delay), add a fetch timeout per endpoint, and stop polling when the tab is hidden (`document.visibilitychange`). | S |
| P-6 | P2 | Font loading | `globals.css` sets `body { font-family: Arial, Helvetica, sans-serif; }`, overriding the Geist variable fonts that `layout.tsx` loads via `next/font/google`. Baseline network capture shows two webfonts downloaded (22.9 KB + 28.9 KB) that are then never actually rendered — Arial wins on `body`. | `src/app/globals.css:28-31` (hardcoded `font-family: Arial...`) vs. `src/app/layout.tsx:7-15` (`geistSans`/`geistMono` loaded) and `globals.css:18-22` (`@theme inline` defines `--font-sans`/`--font-mono` but nothing applies them to `body`) | Either delete the Geist font imports in `layout.tsx` (save ~51 KB/page) or apply `font-sans` (the Tailwind utility backed by `--font-sans`) to `body` and drop the Arial override — pick one, not both. | S |
| P-7 | P2 | Theme FOUC | `ThemeInit` is a client component using `useLayoutEffect` to strip the `dark` class for light-theme users, but the server-rendered HTML always ships with `className="... dark"` hardcoded in `layout.tsx`. Because this runs after hydration rather than as a blocking inline `<script>`, light-theme visitors see a flash of dark theme on every load, worse on slow mobile connections (6.7s LCP page). | `src/app/layout.tsx:50` (`dark` hardcoded in `className`), `src/components/ThemeInit.tsx:1-10` (`"use client"` + `useLayoutEffect`, no blocking script) | Replace with a tiny inline `<script>` in `<head>` (via `dangerouslySetInnerHTML`) that reads `localStorage` and sets the class before paint — the standard no-FOUC pattern — instead of a client component. | S |
| P-8 | P2 | Language FOUC | `Hub`'s `lang` state defaults (English strings) and only switches to the saved `fr` value inside a `useEffect` after mount; `html lang="en"` is hardcoded in `layout.tsx`. French-preferring visitors see an English-copy flash before the effect fires, same root cause pattern as P-7 but for copy, not just a CSS class. | `src/components/Hub.tsx:130-136` (`localStorage.getItem("lang")` read in `useEffect`, not before render), `src/app/layout.tsx:45` (`lang="en"`) | Same fix family as P-7: read the saved lang before first paint (blocking script setting a cookie/attribute `next.js` middleware or root layout can read) rather than correcting post-hydration. | M |
| P-9 | P2 | Image weight | Baseline flagged a 374 KB logo; source is `public/img/shopping-bag.png` (365.6 KB raw PNG) rendered via `next/image` at 36×36 / 28×28 in `Hub.tsx`. The `/_next/image` optimizer is doing its job (baseline §4 shows only 1.7 KB transferred for the optimized request), so the *served* weight is already fine — the risk is the 365 KB source sitting unoptimized in the repo/build output and the `opengraph-image.tsx` route reading the same raw 365 KB file server-side on every OG image render. | `public/img/shopping-bag.png` (365.6 KB per `ls -la`), `src/components/Hub.tsx:498,510` (`next/image`, 36×36/28×28), `src/app/opengraph-image.tsx:9` (`readFile` of the raw PNG) | Pre-compress the source PNG (or convert to WebP) before it lands in `public/img/` — cuts build-time I/O and `opengraph-image` render cost even though the client-facing `/_next/image` path is already fine. | S |
| P-10 | P3 | Caching headers | Live-site response has `cache-control: public, max-age=0, s-maxage=60, must-revalidate` with `x-nextjs-stale-time: 300` — reasonable for an ISR-style homepage, but `max-age=0` means every browser revalidates on each navigation even though the CDN (`s-maxage=60`) already has a fresh copy; no client-side caching headroom is given. | `docs/review/00-baseline.md` §5 header dump | Consider a small client `max-age` (e.g. 10-30s) alongside the existing `s-maxage=60` so repeat navigations within a short window skip the revalidation round-trip entirely. | S |
| P-11 | P3 | `next start` / standalone mismatch | Baseline's local server printed `"next start" does not work with "output: standalone" configuration` — the production start command used for local Lighthouse runs is not the one the deploy actually uses, so any production-start-specific cost (or savings) in `node .next/standalone/server.js` is unmeasured here. | `docs/review/00-baseline.md` §2 intro note | Standardize local perf-testing scripts on `node .next/standalone/server.js` to match the real deploy path, then re-run Lighthouse for a true comparison. | S |
| P-12 | P3 | Turbopack tracing warning | Build emits 3 warnings about `fs.readdirSync`/`path.join` on a non-statically-scoped path in `src/lib/posts.ts`, flagged as a potential full-project bundling/deploy-size risk for the dynamic routes that import it (`/updates`, `/updates/rss.xml`). | `docs/review/00-baseline.md` §1 build warnings, `src/lib/posts.ts:46-47` (`path.join(process.cwd(), contentDir)` + `fs.readdirSync(dir)`) | Pass a statically-analyzable path (e.g. precomputed constant per content dir, already close — `CONTENT_DIR` constants exist in `postmortems.ts`/`updates.ts`) or move the content read behind a build-time script so Turbopack isn't tracing the whole project for these dynamic routes. | M |

## Notes on scope
- Mobile vs desktop: every finding above cites baseline numbers where both exist; the gap between mobile (66 Perf, 6.7s LCP) and desktop (100 Perf, 0.5s LCP) on `/` is driven by P-3 through P-6 combined, not any single cause — mobile throttling simply exposes costs desktop's fast CPU/network hides.
- Did not re-measure; all numbers are from `docs/review/00-baseline.md` and the Lighthouse JSON it references, per instructions.
