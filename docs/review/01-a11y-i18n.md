# Accessibility + i18n Review

Reviewer scope: WCAG AA contrast, keyboard/focus, button-vs-link semantics, iframe titles, `lang` correctness, untranslated strings, FR crawlability. Evidence drawn from `docs/review/axe/*.json`, `docs/review/00-baseline.md`, and direct inspection of `src/`.

| ID | Severity | Area | Problem | Evidence | Fix | Effort |
|---|---|---|---|---|---|---|
| A1 | P1 | i18n/SEO | FR is a client-side-only toggle, not a real crawlable locale. `<html lang="en">` is hardcoded server-side and never varies per route; there is no `/fr` route and no `alternates.languages`/hreflang in metadata. Crawlers and first paint always see English, and the saved preference lives only in `localStorage`. | `src/app/layout.tsx:50` (`lang="en"` literal); `src/app/layout.tsx:19-41` (metadata has `alternates.types` for RSS but no `languages`); `grep -r hreflang src` → 0 matches; `src/components/DocumentationPageClient.tsx:17-27` sets `document.documentElement.lang` only after mount via `localStorage`. | Serve real FR routes (or at minimum per-request `lang` via middleware/cookie + `hreflang` alternates) instead of a post-hydration DOM mutation. | L |
| A2 | P1 | Contrast | `color-contrast` (serious) fires on every single page scanned, 44–88 nodes each, from zinc-500/600 text on zinc-950/white backgrounds at small sizes. | `docs/review/axe/home.json`: nav links `a[href$="infrastructure"]` etc., "insufficient color contrast of 4.12 ... foreground #71717b, background #09090b" (needs 4.5:1); same pattern repeats in `infrastructure.json`, `postmortems.json` (88 nodes), `about.json`, `postmortem-detail.json`, `documentation.json`. | Replace `text-zinc-500`/`text-zinc-600` (and dark-mode `dark:text-zinc-500/600`) on small/body text with a shade that clears 4.5:1 (e.g. zinc-400 on `zinc-950`, zinc-600 on white) sitewide. | M |
| A3 | P1 | Contrast / link semantics | `/documentation` additionally fails `link-in-text-block` (serious, 45 nodes): orange inline links (`#FF8225`) sit at ~1.05:1 contrast against surrounding gray text and only gain an underline on `:hover`, so they're indistinguishable from body text by both color and style at rest. | `docs/review/axe/documentation.json`: `link-in-text-block` nodes e.g. `#dev-0 ... [href$="#int-tailscale"]`, "link text: #ff8225, surrounding text: #9f9fa9 ... has no styling (such as underline) to distinguish it"; source pattern `hover:underline text-[#FF8225]` in `src/components/HomelabDocsContent.tsx`. | Make the underline (or a sufficiently distinct color) the default state, not hover-only. | S |
| A4 | P2 | Semantic structure | No page in the app has a `<main>` landmark at all, causing `landmark-one-main` (moderate) and `region` (moderate, up to 20 nodes) on every route. | `grep -rn "<main" src/app src/components` → 0 results; axe violations present in all 6 saved JSON files (`home`, `infrastructure`, `documentation`, `postmortems`, `postmortem-detail`, `about`). | Wrap each page's primary content in a single `<main>` element. | S |
| A5 | P2 | Keyboard focus | The Documentation page's filter input disables the default focus outline without supplying a replacement focus ring; only a subtle border-color change (`focus:border-zinc-400`) remains, which itself fails the A2 contrast issue. | `src/components/HomelabDocsContent.tsx:330`: `className="... focus:border-zinc-400 focus:outline-none ..."`. No `focus-visible:ring*` anywhere in the codebase (`grep -rl "focus-visible\|focus:ring" src` → no matches besides this file's `focus:outline-none`). | Add a visible `focus-visible:ring-2` (or keep the native outline) instead of just `outline-none`. | S |
| A6 | P2 | i18n | `CookieBanner` is entirely hardcoded English ("This site uses `localStorage`...", "Got it") and never reads the app's language state — it doesn't even import `Lang`/`strings`, unlike every other chrome component. It's rendered on every page via the root layout, so FR visitors always see an English cookie notice. | `src/components/CookieBanner.tsx:26-37` (no `lang`/`strings` import, hardcoded text); contrast with `src/lib/strings.ts` which defines full en/fr dictionaries used by other components; `src/app/layout.tsx:57` mounts it globally. | Wire `CookieBanner` into `strings.ts`/`Lang` the same way `DocumentationPageClient` does. | S |
| A7 | P2 | i18n | `PodBadge` ("Served by Kubernetes pod", "Refresh pod" tooltip) is hardcoded English with no lang awareness, shown on the homepage regardless of selected language. | `src/components/PodBadge.tsx:23` (`<p>Served by Kubernetes pod</p>`), `:32` (`title="Refresh pod"`) — no `Lang`/`strings` import. | Same fix pattern as A6. | S |
| A8 | P2 | i18n | The Documentation tab's actual body content (`HomelabDocsContent`, 458 lines) is not translated at all — only the page header/nav labels come from `strings[lang]` via `DocumentationPageClient`; the component itself takes no `lang` prop and has zero language branching, so toggling to FR changes the header but leaves the whole doc body in English. | `src/components/DocumentationPageClient.tsx:54` renders `<HomelabDocsContent />` with no `lang` prop; `grep -n "lang" src/components/HomelabDocsContent.tsx` returns no real language-branching hits (only an unrelated `document.body.style.overflow` string match). | Either translate the content via `strings.ts`, or scope the i18n claim ("FR available for site chrome only") and disable/hide the toggle on this route until content is translated. | L |
| A9 | P3 | i18n | Postmortem detail pages (`/postmortems/[slug]`) ship no `LanguageToggle` (and no `ThemeToggle`) at all, so FR is unreachable from that template entirely — consistent with the baseline's screenshot gap (only 2/8 EN/FR×light/dark/mobile/desktop combinations exist because the controls don't exist). | `docs/review/00-baseline.md` §3: "this page's header has no language-toggle or theme-toggle controls at all"; confirmed no `LanguageToggle`/`ThemeToggle` import in `src/app/postmortems/[slug]/page.tsx`. | Add the standard header controls to the postmortem detail template. | M |
| A10 | P3 | Button vs link semantics | `BackLink` renders a `<button>` whose click handler calls `router.push("/")` as a real-navigation fallback (when there's no browser history), so in that fallback case a screen-reader/keyboard user gets "button" semantics for what is effectively a link to `/`. | `src/components/BackLink.tsx:9-17` (`<button onClick={() => { if (window.history.length > 1) router.back(); else router.push("/"); }}>`). | Low-risk as-is (back buttons are conventionally buttons); if changed, branch rendering to a real `<Link href="/">` for the fallback path. | S |

## Not flagged / out of scope
- iframe `title`: the homepage's `ProjectPreview` iframe does set a `title` prop (`src/components/ProjectPreview.tsx:125`); did not verify the title text is non-empty/descriptive at the call site for every usage — worth a quick manual spot-check but not flagged as a defect here.
